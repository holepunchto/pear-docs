The clearest answer to "what can I build with this?" is what has already been built. The pages in this section take a shipped application and map it onto the stack these docs describe: which layer handles identity, which handles storage, where the Bare worker boundary sits, and how the app reaches and updates its users without a server.

They are for understanding, not doing. Each page ends with the tutorial, how-to, and reference pages that teach the same techniques, so you can go from "Keet does this" to "here is how" in one click.

These two are documented here because one is the largest Pear app in production and the other is fully open source, so its architecture can be read rather than inferred. The wider ecosystem—including QVAC, Holesail, and community apps—is listed at [pears.com/apps](https://pears.com/apps).

## The pattern they share

Both apps follow the shape [How the stack fits together](/p2p/explanation/how-the-stack-fits-together) recommends and [Pear desktop application architecture](/pear/explanation/pear-desktop-architecture) takes apart: a portable JavaScript **core** that owns the peer-to-peer logic and runs in a Bare worker, and a thin **UI host** per platform—Electron on desktop, a native shell with a Bare worklet on mobile. The official [`hello-pear-electron`](https://github.com/holepunchto/hello-pear-electron) template is that same shape with the product removed, which is why [Getting started](/pear/getting-started) ends there.
