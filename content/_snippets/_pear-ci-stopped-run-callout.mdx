<Callout type="warning">
Don't stop a run after it prints `starting stage for key` while a peer is connected. From that line on, the run writes the release, and a connected peer can learn the release's new length before it has every block. If a timeout or a cancel stops the run at that point, the peer keeps the new length but misses blocks that only the stopped runner had. `pear-ci` 0.1.2 can't recover from this state: later runs fail with `Core <key> length (<n>) is higher than length in snapshot.json`, and a snapshot edited to the new length leaves the run waiting at `waiting synced remote peers` until it times out.

The job log doesn't show peer connections, so check the seeder instead. `pear seed` prints a `peer join` line for each peer that connects, the runner included, and while it's still downloading, its **Drive Length** and **Blobs Length** rows show synced and total blocks, such as `1532/1646`.
</Callout>
