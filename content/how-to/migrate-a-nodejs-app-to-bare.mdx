This guide walks through porting a small existing Node.js app to run on [Bare](/explanation/bare-runtime), standalone (no Pear involved). For the conceptual background on what's actually changing as you do this, see [Migrating from Node.js](/explanation/migrating-from-nodejs).

The example app below is deliberately minimal—it writes a status file with `fs`, resolves a path with `path`, and reads a value off `process`—so the port is easy to follow end to end. The same steps apply to a larger app; you'll just be touching more files.

You'll need the [`bare` CLI](/reference/bare/cli) on your `PATH` to run the ported app:

```sh skip="install-instruction"
npm i -g bare
```

## Swap builtins for `bare-*` modules

Bare doesn't bundle `fs`, `path`, or `process`—each is an installable module you add explicitly (see [The standard library is opt-in, not built in](/explanation/migrating-from-nodejs#the-standard-library-is-opt-in-not-built-in)). Install the equivalents:

```sh example=migrate-nodejs-to-bare step=setup
cd app
npm install bare-fs bare-path bare-process
```

This installs the following dependencies:

- [`bare-fs`](/reference/bare/modules/bare-fs): file system access; its API closely follows Node's `fs`.
- [`bare-path`](https://github.com/holepunchto/bare-path): path manipulation, mirroring Node's `path`.
- [`bare-process`](https://github.com/holepunchto/bare-process): process control, mirroring Node's `process`.

## Run it under Bare

Run the same app with the [`bare` CLI](/reference/bare/cli) instead of `node`:

```sh example=migrate-nodejs-to-bare step=run process=bare-run expect="runtime: bare"
bare app
```

Same output, different runtime—that's the whole port for a script that only touches builtins.

## Handle third-party dependencies that assume Node builtins

Real apps usually have dependencies that themselves `require('fs')` or similar, and you can't edit their source. Alias the builtin name to a [`bare-node`](https://github.com/holepunchto/bare-node) wrapper at install time and the unmodified `require('fs')` inside that dependency resolves to `bare-fs`:

```sh skip="install-instruction"
npm i bare-fs fs@npm:bare-node-fs
```

Each wrapper is a one-line re-export, so npm only ever includes `bare-fs` once no matter how many dependencies need it. Repeat per builtin your dependency tree touches—see [Running third-party modules written for Node.js](/how-to/troubleshooting#running-third-party-modules-written-for-nodejs) for more.

If you'd rather not track them down one at a time, [`bare-node-runtime`](https://github.com/holepunchto/bare-node-runtime) is a compatibility layer you install once that reinstates Node's globals and provides an import map for Node-targeting packages:

```sh skip="install-instruction"
npm i bare-node-runtime
```

See [Choosing a porting strategy](/explanation/migrating-from-nodejs#choosing-a-porting-strategy) for the tradeoffs. If you're the one maintaining a dependency that must run on both runtimes, use an [import map](/how-to/troubleshooting#writing-a-module-with-support-for-bare--nodejs) in its `package.json` instead of either shim.

## Handle native addons

If the app or a dependency has a native addon (a `.node` file, or a `binding.gyp` in its source), it won't load under Bare unmodified—Node-API addons target Node's ABI, not Bare's:

```sh skip="native-addon-rebuild"
# Option 1: rebuild the addon against Bare's native-addon API
# (see the addon's own build instructions—this varies per addon)

# Option 2: build against Node-API compatibility headers instead
npm install bare-compat-napi
```

This is usually the slowest part of a real migration. If you hit `AddonError: ADDON_NOT_FOUND`, see [Troubleshooting](/how-to/troubleshooting#addonerror-addonnotfound-cannot-find-addon-when-running-bare) for the common causes.

## Where to go from here

A Bare app can be compiled into a single standalone executable—no Node.js, Bare, or anything else required on the machine that runs it—with [`bare-build`](https://github.com/holepunchto/bare-build). See [Using Bare on its own](/explanation/use-bare-standalone) for that path, or [Bundle a Bare app](/how-to/run-on-native/bundle-a-bare-app) to package it for embedding in a native app.

If you're instead migrating code toward a peer-to-peer Pear app, the Bare app you just ported is the starting point for a [worker](/explanation/workers)—that's a separate step, not covered here.
