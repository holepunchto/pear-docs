This is **part 2 of 3** in the [getting started path](/getting-started). You will add an append-only **local transcript**: every line you or a peer sends is stored under Electron’s [`userData`](https://www.electronjs.org/docs/latest/api/app#appgetpathname) directory, then **replayed into the UI** when the app starts. 

## Before you start

You need the working project from [part 1 — build the peer-to-peer chat](/getting-started/chat) (same Node, npm, and terminal assumptions).

## What you'll change

| Area | Change |
| --- | --- |
| `package.json` | Add [`corestore`](https://www.npmjs.com/package/corestore) and [`bare-path`](https://www.npmjs.com/package/bare-path). |
| `electron/main.js` | Pass a **stable** folder under [`userData`](https://www.electronjs.org/docs/latest/api/app#appgetpathname) for Corestore (see below: same path every launch so history replays; second *concurrent* peer needs its own `userData`). |
| `workers/main.mjs` | Open a Corestore on that folder, append one JSON line per message, replay stored lines on startup before joining the swarm. |

The preload script and renderer keep the same JSON shapes (`peers`, `message`, `ready`) part 1 already uses.

<Step>

### Add dependencies

From the `chat-app` folder run:

```bash
npm install corestore@^7.9.1 bare-path@^3.0.0
```

* [`corestore`](https://www.npmjs.com/package/corestore) manages one on-disk store and hands you named [Hypercores](/reference/building-blocks/hypercore).
* [`bare-path`](https://www.npmjs.com/package/bare-path) is the small path helper Bare workers use instead of Node’s `path` module.

</Step>

<Step>

### Pass storage into the Electron worker

In `electron/main.js`, pass a **stable** folder after the topic when you spawn the worker — the **same path on every launch** for that app install — so Hypercore blocks you wrote yesterday load again after you quit and run `npm start` tomorrow.

Corestore also opens its database **exclusively**. Two **concurrent** Electron processes must **not** point at the same directory (you get **`File descriptor could not be locked`**). Putting **`process.pid`** in the folder name avoids that collision but **breaks persistence**: each run gets a new PID, so you always open an empty store. The usual pattern is: **one stable directory per `userData` profile**, and give the second local peer its **own profile** with Electron’s [`--user-data-dir`](https://www.electronjs.org/docs/latest/api/command-line-switches#--user-data-dir-directory).

Add `fs` next to your other built-in imports:

```js
const fs = require('fs')
```

Find the line that calls `PearRuntime.run` and give the worker a third argument, the storage root. **Keep** spawning the worker on **`did-finish-load`** as in [part 1](/getting-started/chat); the preload **queue** still absorbs replay lines if they arrive before `onMessage` runs.

```js
// ... existing imports (including fs) and topic derivation ...

function createWindow() {
  const win = new BrowserWindow({
    // ... unchanged ...
  })

  const workerPath = path.join(__dirname, '..', 'workers', 'main.mjs')

  // Same folder every time this userData profile starts → transcript survives restart.
  const storageRoot = path.join(app.getPath('userData'), 'pear-chat-core')
  fs.mkdirSync(storageRoot, { recursive: true })

  win.webContents.once('did-finish-load', () => {
    // argv[2] = topic hex, argv[3] = storage root (see worker)
    worker = PearRuntime.run(workerPath, [topic, storageRoot])
    worker.on('data', (data) => {
      if (!win.isDestroyed()) win.webContents.send('chat:from-worker', data.toString())
    })
    worker.stderr.on('data', (data) => {
      console.error('[worker]', data.toString())
    })
    worker.stdout.on('data', () => {})
  })

  win.loadFile(path.join(__dirname, '..', 'renderer', 'index.html'))
}

// ipcMain.handle('chat:send', ...) stays in app.whenReady() with `if (worker)` (part 1).
```

`Bare.argv[2]` stays the topic hex string; `Bare.argv[3]` becomes the folder where the worker opens Corestore. **Hyperswarm still uses the same topic** (derived from your OS username in part 1), so a **second peer** started with a **different** `--user-data-dir` still joins the same room while keeping its **own** transcript on disk.

</Step>

<Step>

### Replace the Bare worker with Corestore + replay

Replace the contents of `workers/main.mjs` with the following. It keeps the Hyperswarm topic behavior from the original worker in [part 1 — build the peer-to-peer chat](/getting-started/chat), adds append-only storage, and emits stored lines before it connects live peers.

```js
import path from 'bare-path'
import Hyperswarm from 'hyperswarm'
import b4a from 'b4a'
import Corestore from 'corestore'

const utf8 = new TextEncoder()

const topic = b4a.from(Bare.argv[2], 'hex')
const storageRoot = Bare.argv[3]

const store = new Corestore(path.join(storageRoot, 'pear-chat-corestore'))
await store.ready()

const core = store.get({ name: 'chat-transcript' })
await core.ready()

// Replay anything already on disk so the UI matches the last session
for (let i = 0; i < core.length; i++) {
  Bare.IPC.write(b4a.toString(await core.get(i)))
}

const swarm = new Hyperswarm()
const conns = []

swarm.on('connection', (conn) => {
  const id = b4a.toString(conn.remotePublicKey, 'hex').slice(0, 6)
  conns.push(conn)
  Bare.IPC.write(JSON.stringify({ type: 'peers', count: conns.length }))

  conn.on('data', async (data) => {
    const text = b4a.toString(data)
    const payload = JSON.stringify({ type: 'message', from: id, text })
    await core.append(utf8.encode(payload))
    Bare.IPC.write(payload)
  })

  conn.on('error', () => {})
  conn.once('close', () => {
    conns.splice(conns.indexOf(conn), 1)
    Bare.IPC.write(JSON.stringify({ type: 'peers', count: conns.length }))
  })
})

Bare.IPC.on('data', async (data) => {
  const text = b4a.toString(data)
  const payload = JSON.stringify({ type: 'message', from: 'you', text })
  await core.append(utf8.encode(payload))
  for (const conn of conns) conn.write(text)
})

Bare.IPC.write(
  JSON.stringify({
    type: 'message',
    from: 'system',
    text: 'Joining Hyperswarm… (first connect can take a few seconds)'
  })
)

await swarm.join(topic, { client: true, server: true }).flushed()
Bare.IPC.write(JSON.stringify({ type: 'ready' }))
```

Each append stores the exact JSON string the renderer already understands, so you do not need renderer changes for replay.

</Step>

<Step>

### Run it again

```bash
npm start
```

Send messages, **quit the app completely**, then `npm start` again. After replay, prior lines should appear before new live traffic. On disk the store lives under `pear-chat-core` inside Electron’s `userData` tree (for example macOS `~/Library/Application Support/chat-app/pear-chat-core/` when `package.json` `"name"` is `chat-app`).

**Two peers on one machine while testing persistence:** run the first window with `npm start` as usual. The second process needs its **own** `userData` so it does not lock the first Corestore.

In `package.json`, add a script next to `start`:

```json
"scripts": {
  "start": "cross-env ELECTRON_RUN_AS_NODE= electron .",
  "start:peer": "cross-env ELECTRON_RUN_AS_NODE= electron . --user-data-dir=.user-data-peer"
}
```

Create or append a `.gitignore` in the project root so the peer profile is not committed:

```text
.user-data-peer/
```

In a **second** terminal, from the same project folder:

```bash
npm run start:peer
```

Both profiles still use the same OS username, so the **Hyperswarm topic** from part 1 matches and the two windows find each other.

</Step>

</Steps>

## What you added

| Piece | Role |
| --- | --- |
| [Corestore](/reference/helpers/corestore) | One folder-backed store; `get({ name: 'chat-transcript' })` is a dedicated Hypercore for the transcript. |
| Append on send/receive | Every line becomes a Hypercore block — `new TextEncoder().encode(...)` turns JSON strings into UTF-8 bytes for `core.append`. |
| Replay loop | `core.get(i)` before joining the swarm rebuilds the UI from disk (preload queues worker lines until `onMessage` — same as part 1). |

For how Pear lays out application storage when you ship through the platform (not plain Electron `userData`), read [Storage and distribution](/explanation/storage-and-distribution).
