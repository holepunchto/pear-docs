A native addon runs with everything the process can reach. From Bare 1.36.0, an addon package that also ships a WebAssembly build can be loaded as WebAssembly instead, sandboxed through WASI, so the files and system calls it can use are limited to what you grant it. It can still reach anything your JavaScript can, so the sandbox contains a buggy addon, not untrusted code. This guide loads [`bare-sqlite`](/bare/reference/bare/modules/bare-sqlite) this way, gives it one directory for its database, and checks that it can't reach other files.

<Callout type="tip">
For how the sandbox works and what it doesn't stop, read [WebAssembly addons](/bare/explanation/webassembly-addons).
</Callout>

## Before you begin

- Node.js and npm.
- An addon package that ships a `prebuilds/wasi-wasm32/<name>.wasm` build. On Bare 1.36.0 these load: `bare-sqlite` 0.1.5 and later, and `bare-bmp`, `bare-exif`, `bare-gif`, `bare-ico`, `bare-image-resample`, `bare-jpeg`, `bare-png`, `bare-tiff`, and `bare-webp`. `bare-svg` 1.1.1 and `bare-heif` 1.2.1 ship a `.wasm` build that doesn't load yet, because it imports a function that [`bare-wasm-abi`](/bare/reference/bare/modules/bare-wasm-abi#excluded-functions) 0.1.1 doesn't implement.

## Create the project

Install the addon, [`bare-directory`](/bare/reference/bare/modules/bare-directory) and [`bare-wasi`](/bare/reference/bare/modules/bare-wasi) for the sandbox, and Bare 1.36.0 or later as a development dependency, so the project doesn't depend on the version of `bare` on your `PATH`:

```sh example=wasm-sandbox step=setup
mkdir app
cd app
npm init -y
npm i bare-sqlite bare-directory bare-wasi
npm i -D bare
mkdir data
```

The `data` directory is the only part of the file system the addon will see.

## Grant the addon one directory

A WASI provider is a module that exports a function. Bare calls it with the URL of each WebAssembly addon and passes what it returns to `bare-wasi` as the addon's capabilities. Create `app/wasi.js`:

```javascript file=<rootDir>/examples/how-to/run-an-addon-sandboxed-in-webassembly/wasi.js title="app/wasi.js" lineNumbers skip="example-import"
```

{/* @harness example=wasm-sandbox step=copy from=examples/how-to/run-an-addon-sandboxed-in-webassembly/wasi.js to=app/wasi.js */}

`version: 'preview1'` is required. `preopens` maps paths that the addon sees to directories: here, the addon's `/` is your `data` directory. `DirectorySync.open()` opens it as a [`bare-directory`](/bare/reference/bare/modules/bare-directory) capability, confined to that directory in JavaScript and, as far as the platform allows, by the kernel. `HostDirectory` from `bare-wasi/host` wraps it as a directory that `bare-wasi` can preopen. Everything you leave out is denied: the addon gets no standard streams, no randomness, no arguments, and no environment variables. It keeps access to clocks.

## Load the addon as WebAssembly

Add the `host` and `wasi` import attributes to the `require()` of the addon. Create `app/app.js`:

```javascript file=<rootDir>/examples/how-to/run-an-addon-sandboxed-in-webassembly/app.js title="app/app.js" lineNumbers {1-3} skip="example-import"
```

{/* @harness example=wasm-sandbox step=copy from=examples/how-to/run-an-addon-sandboxed-in-webassembly/app.js to=app/app.js */}

`host: 'wasi-wasm32'` loads the WebAssembly build of `bare-sqlite`, and of every other addon in the modules this import pulls in. `wasi` names the provider, resolved relative to `app.js`. Write both values as string literals: Bare reads them from the source before the module runs, so it doesn't see a computed value, and the import fails with `ADDON_HOST_INCOMPATIBLE` or `ADDON_WASI_INCOMPATIBLE`. The database path `/books.db` is a path inside the sandbox, so the file is created as `data/books.db`.

Run it:

```sh example=wasm-sandbox step=run process=app cwd=app expect="Foundation"
npx bare app.js
```

```text skip="output"
{ id: 1, title: 'Dune' }
{ id: 2, title: 'Foundation' }
```

## Check the sandbox

Try to open a database outside the granted directory. Create `app/check-sandbox.js`:

```javascript file=<rootDir>/examples/how-to/run-an-addon-sandboxed-in-webassembly/check-sandbox.js title="app/check-sandbox.js" lineNumbers skip="example-import"
```

{/* @harness example=wasm-sandbox step=copy from=examples/how-to/run-an-addon-sandboxed-in-webassembly/check-sandbox.js to=app/check-sandbox.js */}

```sh example=wasm-sandbox step=run process=check cwd=app expect="Blocked: CANTOPEN"
npx bare check-sandbox.js
```

```text skip="output"
Blocked: CANTOPEN
```

This output is the expected result: the open was refused. The native build would create `/tmp/escape.db` on your machine. The WebAssembly build looks for `/tmp` inside `data`, finds nothing, and SQLite fails with `CANTOPEN`.

## Narrow the rights

`DirectorySync.open()` grants every right by default. Pass `rights` to grant fewer, and `bare-directory` refuses the rest with `ENOTCAPABLE`. Which rights an addon needs depends on how it uses files. The WebAssembly build of `bare-sqlite` 0.1.5 locks a database by creating and removing a `<database>.lock` directory next to it, so even reading needs `create` and `remove`. Writing also needs `truncate`, which SQLite uses to shrink the file on `VACUUM` and when it rolls back a transaction:

```javascript skip="variant-of-wasi-js"
// Read only: open the database with new DatabaseSync('/books.db', { readOnly: true })
DirectorySync.open(__dirname + '/data', { rights: ['lookup', 'read', 'create', 'remove'] })

// Read and write
DirectorySync.open(__dirname + '/data', { rights: ['lookup', 'read', 'write', 'create', 'remove', 'truncate'] })
```

`create` and `remove` also let the addon create directories and delete files in `data`. It can't create files without `write`, so the read-only set stops it writing to the database, not changing the directory.

Without `create` or `remove`, or without `truncate` when writing, SQLite fails with `IOERR`. Without `remove`, the first open succeeds but leaves the `data/books.db.lock` directory behind. After that, opening the database still succeeds, but its first statement fails with `BUSY`, whatever the rights, until you delete `data/books.db.lock` while no process has the database open. See [Rights](/bare/reference/bare/modules/bare-directory#rights) for what each right allows.

## Grant more capabilities

The provider can grant more, one capability at a time:

```javascript skip="variant-of-wasi-js"
const { DirectorySync } = require('bare-directory')
const { HostDirectory } = require('bare-wasi/host')
const crypto = require('bare-crypto')

module.exports = (url) => ({
  version: 'preview1',
  args: ['books'],
  env: { LANG: 'C' },
  preopens: {
    '/': new HostDirectory(DirectorySync.open(__dirname + '/data'))
  },
  stdout: (data) => console.log(data.toString()),
  stderr: (data) => console.error(data.toString()),
  random: (buffer) => crypto.randomFillSync(buffer)
})
```

Bare has no `crypto` global, so take random bytes from [`bare-crypto`](/bare/reference/bare/modules/bare-crypto) (`npm i bare-crypto`). An addon written in Rust can need `random`: the `bare-svg` README says its WebAssembly build does, because the Rust standard library seeds its hash maps with it. `url` is a `URL`, so compare `url.href` to grant different addons different capabilities. Set `clock: null` to deny clocks. There is no capability for sockets. See [`WASIOptions`](/bare/reference/bare/modules/bare-wasi#wasioptions) for every option.

## Bundle the app

[`bare-pack`](/bare/reference/bare/modules/bare-pack) bundles the `.wasm` build of an addon imported with the `host` attribute like any other addon. `bare-directory` is a native addon, and a native addon can't load from inside a bundle, so pass `--offload-addons` to write every addon, the `.wasm` build included, next to the bundle.

Inside a bundle, `__dirname` is a path inside the bundle, so `DirectorySync.open(__dirname + '/data')` fails with `not a directory`. Open the data directory from the working directory instead. Install [`bare-os`](/bare/reference/bare/modules/bare-os) and [`bare-path`](/bare/reference/bare/modules/bare-path), and change `app/wasi.js` to:

```javascript skip="bundling-variant"
const { DirectorySync } = require('bare-directory')
const { HostDirectory } = require('bare-wasi/host')
const os = require('bare-os')
const path = require('bare-path')

module.exports = (url) => ({
  version: 'preview1',
  preopens: {
    '/': new HostDirectory(DirectorySync.open(path.join(os.cwd(), 'data')))
  }
})
```

Then bundle the app, and run the bundle from `app`, where `data` is:

```sh skip="bundling-variant"
npm i bare-os bare-path
npm i -D bare-pack
npx bare-pack --offload-addons --out dist/app.bundle app.js
npx bare dist/app.bundle
```

An addon imported without the `host` attribute is bundled only for the hosts you pass. To bundle its `.wasm` build as a fallback, add `--host wasi-wasm32` to the native hosts: it's used only for addons with no native build for them. `--host wasi-wasm32` on its own bundles only `.wasm` builds.

## Fix common errors

| Error | Cause | Fix |
| --- | --- | --- |
| `UNKNOWN_ADDON_HOST: Addon host '…' is not supported` | The `host` attribute is not `wasi-wasm32`. | Use `host: 'wasi-wasm32'`. |
| `ADDON_NOT_FOUND` | The package, or a package it imports, has no `.wasm` build. | Check that `prebuilds/wasi-wasm32/` exists in the package, or import the package without `host`. |
| `ADDON_HOST_INCOMPATIBLE: Addons of '…' are already resolved for …` | The same package is imported both with and without `host`, or `host` isn't a string literal. A package's addons load one way per process. | Import it with the same attributes everywhere, written as string literals. |
| `ADDON_WASI_INCOMPATIBLE: Addons of '…' are already given …` | Imports of the same package have different `wasi` attributes: two providers, a provider in one and none in another, or a value that isn't a string literal. A dynamic `import()` with a `wasi` attribute also throws it on Bare 1.36.0, even with the same provider. | Use one provider in every import, and grant different addons different capabilities with its `url` argument. |
| `TypeError: WASI provider '…' must export a function` | The provider exports an object. | Export a function that returns the options. |
| `WASIError: INVALID_VERSION` | The options have no `version: 'preview1'`. | Add it. |
| `WASIError: INVALID_PREOPEN: Preopen '/' is not a directory` | A preopen isn't a `bare-wasi` directory, such as a `DirectorySync` that isn't wrapped. | Wrap it: `new HostDirectory(DirectorySync.open(…))`. |
| `WebAssembly addon imports unsupported functions` | The addon's `.wasm` build uses a libjs function that `bare-wasm-abi` doesn't provide. | Use the native build. See [excluded functions](/bare/reference/bare/modules/bare-wasm-abi#excluded-functions). |
| `CANTOPEN` from SQLite | The path is outside the preopened directories, there is no provider, or the directory lacks `lookup` (or `write`, when writing). | Use a path under a preopen, such as `/books.db`, and grant the rights in [Narrow the rights](#narrow-the-rights). |
| `IOERR` or `BUSY` from SQLite | The directory lacks a right SQLite needs, or a stale `<database>.lock` directory was left behind. | See [Narrow the rights](#narrow-the-rights). |

`UNKNOWN_ADDON_HOST`, `ADDON_HOST_INCOMPATIBLE`, and `ADDON_WASI_INCOMPATIBLE` are thrown while Bare links the importing module, before any of its code runs, so a `try` block around a `require()` with a string-literal specifier doesn't catch them. Fix the import instead. `ADDON_NOT_FOUND` is thrown when the module that loads the addon runs, and can be caught.
