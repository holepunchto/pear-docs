This guide walks through a working Bluetooth chat between two phones, with no network in between. The reference implementation is the Bluetooth screen of [`bare-mobile-doctor`](https://github.com/holepunchto/bare-mobile-doctor), Holepunch's diagnostics app for Bare on mobile. It's an Expo app with this split:

- Every Bluetooth call runs in a Bare [worklet](/bare/reference/bare/bare-kit#worklet), through [`bare-bluetooth`](/bare/reference/bare/modules/bare-bluetooth).
- The React Native screen only draws what the worklet reports.

Every phone can advertise and scan at the same time. The screen has a **Discoverable** switch and a **Scan** switch, and either phone can invite the other. You tap a nearby phone to invite it, the other side accepts, and from then on messages travel over an L2CAP channel between the two.

<Callout type="tip">
For how the pieces fit together, read [Bluetooth in Bare](/bare/explanation/bluetooth) first. For why the code waits, normalizes, and times out where it does, read [Bluetooth best practices](/bare/explanation/bluetooth/best-practices).
</Callout>

<Callout type="info">
`bare-bluetooth` is experimental upstream, so its API may change. This guide follows `bare-mobile-doctor` at commit [`5bfe51b`](https://github.com/holepunchto/bare-mobile-doctor/tree/5bfe51b288fa66ed524502fd46fff3ef2038b4fe), which depends on `bare-bluetooth` `^0.6.3`.
</Callout>

## Before you begin

- Two physical phones, iOS or Android in any mix. Simulators and emulators can't stand in for the radio, and upstream warns that emulated Android devices can crash under QEMU.
- Android 12 (API level 31) or later: the app sets [`minSdkVersion`](https://developer.android.com/guide/topics/manifest/uses-sdk-element) to 31.
- The toolchain for the platforms you build: Xcode for iOS, and Android Studio with the SDK, NDK and JDK versions listed in the upstream [README](https://github.com/holepunchto/bare-mobile-doctor#android).
- The [`patchelf`](https://github.com/NixOS/patchelf) binary, which upstream's README asks for before `npm install`.
- Familiarity with running Bare in a React Native app, covered in [Embed Bare in a React Native app](/bare/how-to/run-on-native/embed-bare-in-react-native).

## Clone and run

```bash skip="install-instruction"
git clone https://github.com/holepunchto/bare-mobile-doctor
cd bare-mobile-doctor
npm install
npm run link
npm run bundle
```

These commands do the following:

- `npm run link` links the native addons that the worklets load, `bare-bluetooth` among them, into [`react-native-bare-kit`](https://github.com/holepunchto/react-native-bare-kit). Run it again after every reinstall.
- `npm run bundle` packs every worklet, including the Bluetooth worklet, with [`bare-pack`](/bare/reference/bare/modules/bare-pack).
- If your npm config has `ignore-scripts=true`, run the install script of `@shopify/react-native-skia` by hand. Upstream's [README](https://github.com/holepunchto/bare-mobile-doctor#usage) has the command.

Then build and install on each phone:

```bash skip="native-build"
npm run ios
npm run android
```

`npm run ios` is [`expo run:ios`](https://docs.expo.dev/more/expo-cli/#compiling), which offers simulators as well as devices, so pick your iPhone. Installing on a physical iPhone needs a development team and a provisioning profile. Upstream's [iOS release build steps](https://github.com/holepunchto/bare-mobile-doctor#release-builds) walk through them in Xcode. For Android, upstream's [README](https://github.com/holepunchto/bare-mobile-doctor#android) also lists a Gradle wrapper downgrade to apply after [`expo prebuild`](https://docs.expo.dev/workflow/prebuild/). Without the downgrade, the Android build can fail.

For two Android phones, upstream recommends a release build, which doesn't need a Metro dev server per device:

```bash skip="native-build"
npx expo run:android --variant release --no-bundler
```

You can then install the release APK on the second phone with [`adb`](https://developer.android.com/tools/adb), without rebuilding:

```bash skip="native-build"
adb -s <serial> install -r android/app/build/outputs/apk/release/app-release.apk
```

On both phones, open the Bluetooth screen and allow Bluetooth access when asked. Then:

1. Turn on **Discoverable** on one phone. It starts advertising.
2. Turn on **Scan** on the other. The first phone appears in the device list.
3. Tap **Invite** next to it. The first phone shows the invite. Tap **Accept**.
4. Type messages on either side. **Disconnect** ends the chat on both.

## How a chat starts

The worklet builds three objects. Both phones run all three, so either one can invite the other:

- [`BLECentral`](https://github.com/holepunchto/bare-mobile-doctor/blob/5bfe51b288fa66ed524502fd46fff3ef2038b4fe/bare/bluetooth.js#L106) scans and connects.
- [`BLEServer`](https://github.com/holepunchto/bare-mobile-doctor/blob/5bfe51b288fa66ed524502fd46fff3ef2038b4fe/bare/bluetooth.js#L281) advertises and accepts.
- [`Session`](https://github.com/holepunchto/bare-mobile-doctor/blob/5bfe51b288fa66ed524502fd46fff3ef2038b4fe/bare/bluetooth.js#L423) runs the invite and chat protocol on top of whichever link opens first.

```js file=<rootDir>/examples/how-to/connect-over-bluetooth/bare-mobile-doctor/bare/bluetooth.js#L679-L689 title="bare/bluetooth.js" skip="example-import"
```

Here is what happens between the inviting phone (the central) and the invited one (the server):

```mermaid skip="diagram"
sequenceDiagram
  participant C as Inviter (Central)
  participant S as Invitee (Server)
  S->>S: poweredOn: addService(PSM characteristic), publishChannel()
  S->>S: serviceAdd + channelPublish(psm): startAdvertising()
  C->>C: poweredOn: startScan([SERVICE_UUID])
  S-->>C: advertisement (discover)
  C->>S: connect()
  C->>S: discoverServices, discoverCharacteristics
  C->>S: read(PSM characteristic)
  S-->>C: readRequest answered with the PSM
  C->>S: openL2CAPChannel(psm)
  Note over C,S: channelOpen on both sides
  C->>S: { t: 'invite' }
  S-->>C: { t: 'accept' }
  C->>S: { t: 'msg' } (both ways)
```

### 1. Wait for the radio

Nothing works until the adapter reports [`'poweredOn'`](/bare/reference/bare/modules/bare-bluetooth#bluetoothstate). Before then, [`central.startScan()`](/bare/reference/bare/modules/bare-bluetooth#centralstartscanserviceuuids-options) throws, and turning Bluetooth off drops the services that a server has added. The central re-emits the state, and starts a scan that the user asked for while the radio was still off:

```js file=<rootDir>/examples/how-to/connect-over-bluetooth/bare-mobile-doctor/bare/bluetooth.js#L125-L132 title="bare/bluetooth.js" skip="example-import"
```

The server does its setup in `_start()`, which it calls from its constructor and again on every `'poweredOn'`:

```js file=<rootDir>/examples/how-to/connect-over-bluetooth/bare-mobile-doctor/bare/bluetooth.js#L351-L357 title="bare/bluetooth.js" skip="example-import"
```

<Callout type="warn">
This sample has a gap. `_start()` skips [`server.addService()`](/bare/reference/bare/modules/bare-bluetooth#serveraddserviceservice) once `serviceAdded` is true, and skips [`server.publishChannel()`](/bare/reference/bare/modules/bare-bluetooth#serverpublishchanneloptions) once it holds a PSM. Nothing resets either flag when the radio goes off. After a Bluetooth toggle, an Android phone would advertise with no service and a stale PSM, because `bare-bluetooth` closes the GATT server there. To survive that, clear both flags when the state leaves `'poweredOn'`. See [Wait for `poweredOn`, every time](/bare/explanation/bluetooth/best-practices#wait-for-poweredon-every-time).
</Callout>

### 2. Publish a channel and serve its PSM

An L2CAP channel is identified by a PSM number that the operating system picks when you publish it, so the other phone can't know it in advance. The server solves that with a GATT [`Service`](/bare/reference/bare/modules/bare-bluetooth#const-service--new-serviceuuid-characteristics-options) that holds one readable [`Characteristic`](/bare/reference/bare/modules/bare-bluetooth#const-characteristic--new-characteristicuuid-options), `PSM_UUID`. It answers every read of that characteristic with the PSM, as text, through [`server.respondToRequest()`](/bare/reference/bare/modules/bare-bluetooth#serverrespondtorequestrequest-result-data):

```js file=<rootDir>/examples/how-to/connect-over-bluetooth/bare-mobile-doctor/bare/bluetooth.js#L5-L12 title="bare/bluetooth.js" skip="example-import"
```

### 3. Advertise once both are ready

A central that connects before the service exists, or before there is a PSM to read, gets nothing. So `startAdvertising()` advertises only once the [`serviceAdd`](/bare/reference/bare/modules/bare-bluetooth#server) and [`channelPublish`](/bare/reference/bare/modules/bare-bluetooth#server) events have both fired. Until then, it records the request, and those two handlers call it again:

```js file=<rootDir>/examples/how-to/connect-over-bluetooth/bare-mobile-doctor/bare/bluetooth.js#L372-L397 title="bare/bluetooth.js" skip="example-import"
```

`BLEServer` advertises with [`server.startAdvertising()`](/bare/reference/bare/modules/bare-bluetooth#serverstartadvertisingoptions). The advertisement carries the service UUID, which is what the other phone filters its scan on.

### 4. Scan for the service

The central scans only for peripherals that advertise the chat's service UUID. On Android, it also passes the low-latency scan mode (the `scanOptions` constant in step 2). That mode is already the default of `bare-bluetooth-android`, so passing it only makes the choice explicit:

```js file=<rootDir>/examples/how-to/connect-over-bluetooth/bare-mobile-doctor/bare/bluetooth.js#L226-L237 title="bare/bluetooth.js" skip="example-import"
```

Every advertisement arrives as a [`discover`](/bare/reference/bare/modules/bare-bluetooth#central) event with a [`DiscoveredPeripheral`](/bare/reference/bare/modules/bare-bluetooth#discoveredperipheral), often many per phone. The central keeps the latest one per `id` and reports it to the UI:

```js file=<rootDir>/examples/how-to/connect-over-bluetooth/bare-mobile-doctor/bare/bluetooth.js#L134-L143 title="bare/bluetooth.js" skip="example-import"
```

### 5. Connect, find the PSM and open the channel

Tapping **Invite** stops the scan with [`central.stopScan()`](/bare/reference/bare/modules/bare-bluetooth#centralstopscan) and connects to the discovered peripheral with [`central.connect()`](/bare/reference/bare/modules/bare-bluetooth#centralconnectperipheral):

```js file=<rootDir>/examples/how-to/connect-over-bluetooth/bare-mobile-doctor/bare/bluetooth.js#L255-L267 title="bare/bluetooth.js" skip="example-import"
```

Once connected, the central walks down to the PSM one event at a time, on the [`Peripheral`](/bare/reference/bare/modules/bare-bluetooth#peripheral):

1. Discover the service with [`peripheral.discoverServices()`](/bare/reference/bare/modules/bare-bluetooth#peripheraldiscoverservicesserviceuuids).
2. Discover its PSM characteristic with [`peripheral.discoverCharacteristics()`](/bare/reference/bare/modules/bare-bluetooth#peripheraldiscovercharacteristicsservice-characteristicuuids).
3. Read the characteristic with [`peripheral.read()`](/bare/reference/bare/modules/bare-bluetooth#peripheralreadcharacteristic).
4. Open the channel on the number it reads, with [`peripheral.openL2CAPChannel()`](/bare/reference/bare/modules/bare-bluetooth#peripheralopenl2capchannelpsm).

```js file=<rootDir>/examples/how-to/connect-over-bluetooth/bare-mobile-doctor/bare/bluetooth.js#L170-L224 title="bare/bluetooth.js" skip="example-import"
```

`findByUUID()` doesn't compare UUIDs with `===`. iOS reports them uppercase and Android reports them lowercase, so the function normalizes both sides first:

### 6. Chat over the channel

When the channel opens, both sides get an [`L2CAPChannel`](/bare/reference/bare/modules/bare-bluetooth#l2capchannel), which is a duplex stream. From here on, there is no central or server any more. Each side wraps the channel in a [`PeerLink`](https://github.com/holepunchto/bare-mobile-doctor/blob/5bfe51b288fa66ed524502fd46fff3ef2038b4fe/bare/bluetooth.js#L63), which frames it with [`framed-stream`](https://github.com/holepunchto/framed-stream) so that every write arrives as one whole message, and sends JSON:

```js file=<rootDir>/examples/how-to/connect-over-bluetooth/bare-mobile-doctor/bare/bluetooth.js#L60-L102 title="bare/bluetooth.js" skip="example-import"
```

The chat protocol has five messages, handled in `Session.handlePeerMessage()`:

| Message | Sent by | Meaning |
| --- | --- | --- |
| `{ t: 'invite', n }` | inviter, as soon as the channel opens | "`n` wants to chat" |
| `{ t: 'accept' }` | invitee | start the chat |
| `{ t: 'reject' }` | invitee | decline; the inviter tears the link down |
| `{ t: 'msg', d }` | either | a chat message with text `d` |
| `{ t: 'disconnect' }` | either | the chat is over |

L2CAP is reliable, so a peer that closes the channel shows up as [`close`](/bare/reference/bare/modules/bare-bluetooth#l2capchannel) or `error` on the stream, the same on both platforms. That's why `PeerLink` needs no platform-specific disconnect detection for that case. A peer that vanishes without closing the channel takes longer to notice. See [Notice a peer that has vanished](/bare/explanation/bluetooth/best-practices#notice-a-peer-that-has-vanished).

## Handle failures

On iOS and Android, a failed connection attempt and a disconnect that an error causes both arrive as an [`error`](/bare/reference/bare/modules/bare-bluetooth#bluetootherror) event rather than a [`disconnect`](/bare/reference/bare/modules/bare-bluetooth#central) event. The central routes those two codes, `CONNECTION_FAILED` and `DISCONNECT`, back into the session. Otherwise, the session would stay stuck in "connecting":

```js file=<rootDir>/examples/how-to/connect-over-bluetooth/bare-mobile-doctor/bare/bluetooth.js#L156-L167 title="bare/bluetooth.js" skip="example-import"
```

`bare-bluetooth` sets no timeout on a connection attempt either, so the session sets its own, 15 seconds, and goes back to scanning when it fires:

```js file=<rootDir>/examples/how-to/connect-over-bluetooth/bare-mobile-doctor/bare/bluetooth.js#L601-L612 title="bare/bluetooth.js" skip="example-import"
```

<Callout type="warn">
This timer abandons the session, but it doesn't cancel the pending connection. `BLECentral.disconnect()` acts only once a peripheral has connected, so a late [`connect`](/bare/reference/bare/modules/bare-bluetooth#central) event can still arrive after the timeout. In your own code, call [`central.disconnect()`](/bare/reference/bare/modules/bare-bluetooth#centraldisconnectperipheral) with the object that you passed to `connect()`, the way the Apple test in [Reconnect without scanning](/bare/how-to/connect-over-bluetooth/use-platform-specific-bluetooth-features#apple-reconnect-without-scanning) does.
</Callout>

## Tear down

Ending a chat closes the stream and drops the Bluetooth connection, whichever role this phone played:

```js file=<rootDir>/examples/how-to/connect-over-bluetooth/bare-mobile-doctor/bare/bluetooth.js#L549-L559 title="bare/bluetooth.js" skip="example-import"
```

When the user leaves the screen, the React Native side takes two steps:

1. It sends `disconnect` to the worklet, so the other phone hears about it right away instead of waiting for the Bluetooth supervision timeout.
2. It terminates the worklet a moment later.

```tsx file=<rootDir>/examples/how-to/connect-over-bluetooth/bare-mobile-doctor/app/views/bluetooth/BluetoothTests.tsx#L183-L196 title="app/views/bluetooth/BluetoothTests.tsx" skip="example-import"
```

<Callout type="warn">
On exit, the worklet deliberately skips [`server.destroy()`](/bare/reference/bare/modules/bare-bluetooth#serverdestroy) and [`central.destroy()`](/bare/reference/bare/modules/bare-bluetooth#centraldestroy). A comment in the code says that on iOS the native module's runtime-teardown cleanup frees the same handle a second time after an explicit `destroy()`, and crashes. `bare-bluetooth-apple` fixed that cleanup in July 2026, before the comment was written, so the workaround may be out of date. Test teardown on a device before you copy it or drop it. See [Clean up in the right order](/bare/explanation/bluetooth/best-practices#clean-up-in-the-right-order).
</Callout>

## Remix it

The channel is a plain duplex stream, so the chat is only one use of it:

| Build | Change |
| --- | --- |
| File or photo transfer | Keep `PeerLink`'s framing and send binary frames instead of JSON. |
| A protocol of your own | Replace `Session.handlePeerMessage()` and the `t` tags. The discovery and channel code stays as it is. |
| Encrypted, replicating peers | Use [`ble-swarm`](https://github.com/holepunchto/ble-swarm) instead. It runs a [Noise](https://noiseprotocol.org/) handshake over each Bluetooth connection and hands you the same kind of encrypted stream as [Hyperswarm](/p2p/reference/building-blocks/hyperswarm), ready for [`corestore.replicate()`](/p2p/reference/helpers/corestore#storereplicateoptsorstream). |
